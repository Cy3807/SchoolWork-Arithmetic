## 二、需求理解

程序分为生成和批改两种模式。生成时，`-n` 指定题目数量，`-r` 指定操作数和分数分母的上限，不包含上限本身。题目写入 `Exercises.txt`，对应答案写入 `Answers.txt`。批改时，用 `-e`、`-a` 分别指定题目文件和学生作答文件，结果保存到 `Grade.txt`。

实现中需要注意两点。第一，不能只检查最后的答案是否非负，所有减法子表达式都要满足要求；除法子表达式也必须得到严格大于 0、小于 1 的分数。第二，题目是否重复取决于运算结构，不能仅看算式文字或答案。

例如，`3+(2+1)` 和 `1+2+3` 可以通过交换加法两侧的子表达式得到同一棵树，因此算重复。`1+2+3` 与 `3+2+1` 虽然结果相同，但按作业规定不算重复。这一区别决定了去重时必须保留括号对应的结构。

## 三、程序设计

程序按职责拆成四个部分：

| 文件 | 主要作用 |
| --- | --- |
| `Myapp.py` | 读取参数，选择生成或批改模式，处理错误提示 |
| `quiz/model.py` | 分数处理、表达式树、题面输出和表达式解析 |
| `quiz/generate.py` | 随机生成合法题目并去重 |
| `quiz/files.py` | 文件读写、题号检查和批改统计 |

表达式用二叉树保存。叶子是一个数，其他节点保存运算符、左右子树和计算结果。每次先决定使用 1 至 3 个运算符，再把数量分给左右子树，递归完成一道题。

构造减法时，把数值较大的子表达式放在左边；构造除法时，把较小的正数放在左边。如果这对子树不能组成符合要求的除法，就改用其他运算。这样可以保留已经创建的子树，减少重新生成的次数。

生成完一道题后，程序计算它的规范键，检查是否已经出现。没有重复才加入结果，直到达到指定数量。范围过小而题量过大时，程序会在达到尝试上限后提示调整参数。

## 四、关键实现

### 1. 分数计算

分数统一使用 Python 标准库中的 `Fraction`，避免将分数转成小数后产生误差。

```python
from fractions import Fraction

result = Fraction(1, 6) + Fraction(1, 8)
# 结果为 7/24
```

输出时再处理格式：整数直接输出，真分数写成 `3/5`，假分数转成 `2'3/8` 这样的带分数。批改比较的是数值，因此 `6/4` 和 `1'1/2` 可以判为同一个答案。

### 2. 题目去重

去重的关键代码如下：

```python
def key(self) -> tuple:
    if not self.op:
        return ("n", self.value.numerator, self.value.denominator)

    left, right = self.left.key(), self.right.key()
    if self.op in ("+", "*") and right < left:
        left, right = right, left
    return (self.op, left, right)
```

加法、乘法可以交换两侧，所以将它们的左右键按固定顺序排列。减法、除法保留原顺序。整个键仍然包含子树结构，没有把所有加数或乘数拆开重排。将这些键放入集合，就能检查本批题目是否重复。

### 3. 括号与批改

输出算式时，优先级较低的子表达式需要加括号，同优先级的右子表达式也保留括号。例如 `1+(2+3)` 不能直接输出成 `1+2+3`，否则数值虽然没变，原来的运算结构却变了。

批改程序通过递归下降解析器重新计算题目，再与作答比较。解析分为加减、乘除、数字或括号三层，不使用 `eval`。其中 `3/4` 被识别为一个分数，避免把 `1/2 ÷ 3/4` 错误拆成连续除法。

## 五、性能分析

性能分析工作量按约 35 分钟估算，已计入 PSP 的相关阶段。下面的运行时间则由程序实测获得。

测试环境为 macOS arm64、Python 3.9.6。固定 `r=10` 和随机种子 `20261009`，分别使用列表与集合查重，各运行三次取中位数。两种方式得到相同的候选序列和最终题目，便于比较查重容器的影响。

| 题目数量 | 列表查重耗时（秒） | 集合查重耗时（秒） |
| --- | --- | --- |
| 100 | 0.007026 | 0.008159 |
| 1000 | 0.157539 | 0.069600 |
| 10000 | 10.710707 | 1.792698 |

![性能分析图](https://img2024.cnblogs.com/blog/3846615/202610/3846615-20261009115218393-1811549637.png)

一万道题时，列表方案的耗时约为集合方案的 5.97 倍；只有一百道题时，集合并没有更快。因此，优化效果要结合题量判断。这里的列表方案用于对照实验，数据也会受到电脑后台负载影响。

从 `cProfile` 的结果看，主要时间花在 `build` 和 `random_number`，即建树与生成操作数。图中的累计时间包含子函数调用，不能直接相加。另一轮完整流程中，生成、写文件和批改分别用了 1.187 秒、0.191 秒和 0.892 秒，一万道题全部批改正确。

除集合查重外，程序还在节点创建时保存计算结果，并将文本整理好后整批写入文件。这些处理减少了重复计算和零散写入，但本次没有单独测量它们各自的收益。

## 七、运行方法

在项目目录执行：

```sh
# 生成 10 道题
python3 Myapp.py -n 10 -r 10

# 生成一万道题
python3 Myapp.py -n 10000 -r 10 --seed 20261009

# 批改作答
python3 Myapp.py -e Exercises.txt -a Answers.txt

# 运行测试
python3 tools/check.py
```

Windows 使用 Python 版时，可将 `python3` 换成 `py -3`；也可以下载 `Myapp.exe`，在终端中使用相同参数。再次生成题目会更新同名文件，需要保留多批题目时可指定 `--output-dir`。

## 八、项目小结

这道题看起来是四则运算，实际更考验对需求的理解。尤其是去重规则，如果一开始只按答案或字符串判断，后面的实现再完整也会偏离要求。表达式树把计算、输出和去重放在同一套结构中，比较适合处理这类问题。

本次采用主体实现与独立 AI 复核相结合的方式。复核使用了不同的求值和去重方法，减少了两边沿用同一段代码而共同遗漏问题的可能。固定随机种子、保存输入输出，也让检查结果更容易复现。

目前程序已经覆盖题目生成和批改要求，但题目难度仍然是随机的，尚未按年级分类。小范围下请求大量题目时，除 `r=1` 外也没有精确计算全部容量。后续可以从这两点继续改进。
